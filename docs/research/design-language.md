# macOS 27 design language and official SwiftUI component inventory

Research for [#4](https://github.com/SamWongML/macos-audio-recording/issues/4), part of the map in [#1](https://github.com/SamWongML/macos-audio-recording/issues/1). Answers: what macOS 27's design language actually is, and which of this app's surfaces are covered by official Apple components versus needing a custom or AppKit-bridged control.

## Method and ground truth

Per the ticket's trust order, API existence claims are checked against the installed SDK, not memory or web copy. The SDK on this machine lives under **`/Applications/Xcode-beta.app`** (there is no `/Applications/Xcode.app` here — noted in §5, "what I could not verify"). All SDK paths below are relative to:

```
$SDK = /Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk
```

Confirmed version: `$SDK/SDKSettings.plist` → `Version = 27.0`, `DisplayName = macOS 27.0`; `$SDK/System/Library/CoreServices/SystemVersion.plist` → `ProductUserVisibleVersion = 27.0`.

Two Swift modules matter for SwiftUI API-existence claims, and both are cited by their `arm64e-apple-macos.swiftinterface`:

- **`SwiftUI.swiftinterface`** — `$SDK/System/Library/Frameworks/SwiftUI.framework/Modules/SwiftUI.swiftmodule/arm64e-apple-macos.swiftinterface` (34,178 lines). Holds platform-specific and AppKit-facing API: `MenuBarExtra`, `GlassButtonStyle`, the new `Document` protocols, toolbar placement APIs.
- **`SwiftUICore.swiftinterface`** — `$SDK/System/Library/Frameworks/SwiftUICore.framework/Versions/A/Modules/SwiftUICore.swiftmodule/arm64e-apple-macos.swiftinterface` (27,574 lines). Holds the cross-platform core: `Glass`, `glassEffect`, `GlassEffectContainer`, `ConcentricRectangle`, `EnvironmentValues.appearsActive`.

Every `@available` annotation quoted below was read directly from these files (or, for AppKit/AVFoundation/AVFAudio, from the Objective-C headers under the same SDK), not reconstructed from memory. The [`swiftui-whats-new-27`](../../.claude/skills/swiftui-whats-new-27) and [`swiftui-specialist`](../../.claude/skills/swiftui-specialist) skills were consulted first (per the ticket); their references cover `@State`, toolbar overflow, `reorderable()`, `AsyncImage`, and soft-deprecations generally, but **neither has content specific to Liquid Glass, materials, or `MenuBarExtra`** — that material came from the SDK interfaces, `mcp__xcode__DocumentationSearch` (the HIG and API reference), and the WWDC 2026 "What's New in SwiftUI" session page (`developer.apple.com/videos/play/wwdc2026/269/`, fetched directly).

## (a) The design language rules that apply to this app

### Headline: Liquid Glass's public API surface did not grow in macOS 27 — it shipped in macOS 26 and got tuned, not extended

Every glass-specific SwiftUI type is gated `@available(macOS 26.0, *)`, not 27:

| API | Declaration | File : line | Availability |
|---|---|---|---|
| `Glass` | `public struct Glass : Swift.Equatable, Swift.Sendable` | `SwiftUICore.swiftinterface:7245` | `@available(iOS 26.0, macOS 26.0, tvOS 26.0, watchOS 26.0, *)`, `@available(visionOS, unavailable)` |
| `View.glassEffect(_:in:)` | `nonisolated public func glassEffect(_ glass: Glass = .regular, in shape: some Shape = DefaultGlassEffectShape()) -> some View` | `SwiftUICore.swiftinterface:3064` | same as above |
| `GlassEffectContainer` | `public struct GlassEffectContainer<Content> : View` | `SwiftUICore.swiftinterface:11523` | same as above |
| `PrimitiveButtonStyle.glass` / `.glass(_:)` | `public static var glass: GlassButtonStyle` / `static func glass(_ glass: Glass) -> Self` | `SwiftUI.swiftinterface:1472,1475` | `@available(iOS 26.0, macOS 26.0, tvOS 26.0, watchOS 26.0, *)` |
| `GlassButtonStyle.init(_:)` (choose a `Glass` variant directly) | `nonisolated public init(_ glass: SwiftUICore.Glass)` | `SwiftUI.swiftinterface:1483` | `@available(iOS 26.1, macOS 26.1, tvOS 26.1, watchOS 26.1, *)` — a **26.1 point-release** addition, still not 27 |
| `PrimitiveButtonStyle.glassProminent` | `public static var glassProminent: GlassProminentButtonStyle` | `SwiftUI.swiftinterface:4458` | `@available(macOS 26.0, *)` |
| `ConcentricRectangle` (the shape that backs concentric corner radii) | `public struct ConcentricRectangle : Shape, Animatable` | `SwiftUICore.swiftinterface:16935` | `@available(iOS 26.0, macOS 26.0, tvOS 26.0, watchOS 26.0, visionOS 26.0, *)` |
| `View.backgroundExtensionEffect()` | `func backgroundExtensionEffect() -> some View` | `SwiftUI.swiftinterface:15832` | `@available(iOS 26.0, macOS 26.0, tvOS 26.0, watchOS 26.0, visionOS 26.0, *)` |

I grepped both interfaces for every `@available(...macOS 27.0...)` annotation (72 hits in `SwiftUICore`, 79 in `SwiftUI`) and read each one in context. The overwhelming majority are compiler-internal (`_propertyStorageSize` SPI on ~15 different `View`/`Scene`/`ToolbarContent` conformances, a `PreferenceKey._preferenceValuesEqual` SPI, a `TopLeftGlobalSpaceConstant` layout-direction package protocol) — not public design-system API. The handful of genuinely public, design-relevant 27.0 additions are: the `Document`/`DocumentGroup` family (see §5), `reorderable()`/`reorderContainer` (§5), `PickerStyle.tabs` (§3), and `EnvironmentValues.appearsActive` gaining dedicated backing storage (below). **None of them touch materials, glass, corner radii, or spacing.** This matches Apple's own framing at WWDC26 session 269: *"Apps gain this look without having to change a single line of code"* — the 27 story for Liquid Glass is automatic propagation and a user-facing tint slider, not new developer-facing API. (Corroborating but non-authoritative: contemporaneous coverage — [MacRumors](https://www.macrumors.com/2026/06/09/macos-golden-gate-liquid-glass/), [AppleInsider](https://appleinsider.com/articles/26/06/09/dont-get-excited-for-big-liquid-glass-changes-in-macos-27-because-they-arent-there) — describes macOS 27 ("Golden Gate") as adding a Settings-level Liquid Glass tint slider and readability/contrast fixes to the *existing* material, not a new material or API generation. Treated as a lead, not a source, per the ticket's instructions — the WWDC session page is the citation that carries weight here.)

One real macOS-27-specific behavior change: **`EnvironmentValues.appearsActive`** (the replacement for the deprecated `controlActiveState`) is declared once, `@backDeployed(before: macOS 15.0)`, at `SwiftUICore.swiftinterface:14081`, with `@available(iOS 18.0, macOS 10.15, tvOS 18.0, watchOS 11.0, visionOS 2.0, *)`. Its *implementation* branches on `#available(...macOS 27.0...)`: on 27+ it reads/writes a new dedicated `_appearsActive` storage (`SwiftUICore.swiftinterface:14103`, `@available(anyAppleOS 27.0, *)`); pre-27 it falls back to `controlActiveState == .key`. WWDC26 session 269 documents the visible effect: windows now dim their icons/text automatically when inactive, and sample code conditionally reduces a button's opacity "using the `appearsActive` environment value." Relevant to this app because the editor window (Trim/Export) is a normal `WindowGroup`-style scene that will pick this up for free — no custom "is my window key" tracking needed.

### HIG: materials, layering, restraint

Source: `mcp__xcode__DocumentationSearch`, HIG page **Materials** (`/design/Human-Interface-Guidelines/materials` and its `#Liquid-Glass` anchor).

- **Two material families exist**: Liquid Glass (dynamic, for the *functional layer* — controls and navigation) and Standard materials (static blur tiers — ultraThin/thin/regular/thick — for the *content layer*). The HIG is explicit that these are not interchangeable: *"Don't use Liquid Glass in the content layer... Instead, use Standard materials for elements in the content layer, such as app backgrounds."*
- **Restraint is stated directly, twice.** *"Use Liquid Glass effects sparingly... If you apply Liquid Glass effects to a custom control, do so sparingly... Limit these effects to the most important functional elements in your app."* And a related engineering note in the "Applying Liquid Glass to custom views" doc: *"Creating too many Liquid Glass effect containers and applying too many effects to views outside of containers can degrade performance. Limit the use of Liquid Glass effects onscreen at the same time."*
- **Two variants, `.regular` and `.clear`**, with a stated decision rule: use `.regular` (the default) when the background might hurt legibility or content is text-heavy (alerts, sidebars, popovers — this app's control panel and range-selector qualify); reserve `.clear` for glass that floats over rich media (photo/video), which nothing in this app does.
- **Exception carved out for transient interactive controls**: *"An exception is for controls in the content layer with a transient interactive element like Sliders and Toggles; in these cases, the element takes on a Liquid Glass appearance to emphasize its interactivity when a person activates it."* This is a system behavior on the stock `Slider`/`Toggle`, not something to hand-implement.
- **Corner radii are concentric, not hand-picked.** `ConcentricRectangle` / `Edge.Corner.Style.concentric(minimum:)` (`SwiftUICore.swiftinterface:16935`, `17051-17054`) computes a child's corner radius from its container's radius minus the offset between them, falling back to a minimum when that would go negative or square. The HIG's rule of thumb, matched to this API, is: don't invent a corner-radius constant for a custom control nested inside a glass container — let it inherit concentrically.
- **For a small utility app specifically**, the applicable defaults are: `buttonStyle(.glass)` / `.glassProminent` for primary actions (automatic, matches system chrome), `GlassEffectContainer` only if grouping *multiple* custom glass shapes that need to morph/merge (this app likely doesn't — one control panel, not a cluster of custom glass icons), and Standard materials (not Liquid Glass) for the editor window's content background.

### Typography and spacing (macOS specifics)

Source: HIG **Typography** page, `#macOS` and `#macOS-built-in-text-styles` anchors; HIG "Designing for games" `#Look-stunning-on-every-display` (carries the cross-platform default/minimum size and button-size table, macOS row included).

- System font is **SF Pro**; macOS does *not* support Dynamic Type (unlike iOS/iPadOS/tvOS/visionOS/watchOS) — text styles still exist for hierarchy but don't scale with a user-controlled slider on this platform.
- macOS default text size is **13 pt**, minimum recommended **10 pt** (same table lists iOS 17/11, tvOS 29/23, visionOS 17/12, watchOS 16/12).
- macOS built-in text style sizes (HIG table, `#macOS-built-in-text-styles`): Body 13/16 (size/line-height, pt), Callout 12/15, Subheadline 11/14, Footnote 10/13, Caption 1 & 2 10/13, Headline 13/16 (Bold). A small utility panel's labels should sit at Caption/Footnote/Subheadline, not invent point sizes.
- macOS default control/button size **28×28 pt**, minimum **20×20 pt** (vs. iOS 44×44/28×28) — relevant to sizing the transport buttons (play/pause/stop) and any custom hit targets in the range selector.
- For matching system-chrome typography exactly (e.g., a label styled like a menu item or window title), macOS exposes dedicated `NSFont` factory methods — `controlContentFont(ofSize:)`, `menuFont(ofSize:)`, `menuBarFont(ofSize:)`, `titleBarFont(ofSize:)`, etc. (HIG Typography `#macOS`) — bridged in, not SwiftUI-native.

## (b) Component inventory for this app's surfaces

Verdict key: **Official** = a stock SwiftUI (or trivially-bridged AppKit) type does the job as-is. **Bridge** = no SwiftUI type; a documented AppKit type covers it via `NSViewRepresentable`. **Custom** = no first-party primitive; build it, with the reason stated.

| Surface | Official component? | Verdict | Notes / citation |
|---|---|---|---|
| Popover-style control panel off the menu bar | `MenuBarExtra` scene, `.menuBarExtraStyle(.window)` | **Official** | `MenuBarExtra` struct: `SwiftUI.swiftinterface:2092`, `@available(macOS 13.0, *)`. `.window` style: `WindowMenuBarExtraStyle`/`.window` at `SwiftUI.swiftinterface:5952,5975`, same availability. Unchanged since Ventura — see §c below for the HIG tension this creates. |
| Picker for a running application (with icon) | `Picker` + `Label`/`Image(nsImage:)` fed by `NSRunningApplication` | **Official** (bridge for the *data*, not the control) | `Picker` itself is stock SwiftUI. The icon comes from `NSRunningApplication.icon: NSImage?` (`AppKit.framework/Versions/C/Headers/NSRunningApplication.h:115`) rendered via `Image(nsImage:)` (`SwiftUI.swiftinterface:29181`). No custom view needed. |
| Scrubbable audio timeline / playhead | — | **Custom** | No SwiftUI, AVKit, or AVFoundation type exists for this (see waveform section — AVKit's entire macOS SwiftUI surface is `VideoPlayer`, a video-frame view, not reusable for an audio-only scrubber). Build on `Slider` bound to playback position, or a `Canvas`-drawn track if it must show the waveform under the playhead in the same view. |
| Range selector for Trim in/out points | — | **Custom** | `SwiftUI.Slider` has no two-thumb / range-bound initializer (checked every `Slider` init in `SwiftUI.swiftinterface:4841-4939`: all take a single `Binding<V>`, never a `Binding<ClosedRange<V>>`). No `RangeSlider` type exists anywhere in `SwiftUI`/`SwiftUICore`. This is the clearest "must be custom" case in the app — two draggable handles over a `Canvas`/`Shape` track, or two overlapping `Slider`s as a fallback, are the standard workarounds developers use industry-wide; neither is a documented Apple pattern. |
| Transport controls (play/pause/stop) | `Button` with `buttonStyle(.glass)` / SF Symbols (`play.fill`, `pause.fill`, `stop.fill`) | **Official** | Stock `Button` + `Image(systemName:)`. Nothing transport-specific needed. |
| Live audio level meter | — | **Custom** (bridge considered, not recommended) | No SwiftUI type. `Gauge` exists on macOS (`SwiftUI.swiftinterface:25793`, `@available(iOS 16.0, macOS 13.0, watchOS 7.0, *)`) but **only `.automatic`/`DefaultGaugeStyle`** is available there — `.circular` and `.linear` `GaugeStyle`s are explicitly `@available(macOS, unavailable)` (`SwiftUI.swiftinterface:13580,27630`; watchOS-only), so `Gauge` can't be shaped into a classic horizontal VU meter on macOS. `ProgressView` + `LinearProgressViewStyle` (`SwiftUI.swiftinterface:5980`, `@available(iOS 14.0, macOS 11.0, ...)`) is the closest value-bound bar but has no peak-hold or color-zone semantics. AppKit's `NSLevelIndicator` (`AppKit.framework/Versions/C/Headers/NSLevelIndicator.h:25`, `levelIndicatorStyle` continuous/discrete-capacity styles, `API_AVAILABLE(macos(10.10))`) is a real bridge candidate but is designed for discrete/static readouts, not proven for smooth per-frame level animation — a `Canvas`-drawn meter driven by an `AVAudioEngine` tap is the safer choice for a responsive, peak-holding meter. Stated reason for going custom: no official component models "continuously updating amplitude with peak-hold and color zones." |
| Quality/preset picker | `Picker` with `.segmented` or the new `.tabs` style | **Official** | `.segmented`: `SegmentedPickerStyle`, long-standing. `.tabs`: `TabsPickerStyle`/`PickerStyle.tabs`, new in this SDK — `SwiftUI.swiftinterface:16647,16653`, `@available(iOS 27.0, macOS 27.0, tvOS 27.0, visionOS 27.0, *)`. For 3–5 named Quality Presets, either style is a stock fit; `.tabs` is genuinely macOS-27-new and worth using per the "prefer new official APIs" instruction in the "what's new" section below. |
| File-size estimate readout | `Text` with `.formatted(.byteCount(...))` | **Official** | Plain text formatting, no special component required. |
| Export progress | `ProgressView(value:total:)` | **Official** | `ProgressViewStyle`/`ProgressView` are stock and platform-appropriate (`LinearProgressViewStyle`, `SwiftUI.swiftinterface:5980`). |

**Summary: 6 of 8 surfaces are covered by official components** (popover panel, app picker, transport controls, quality picker, size readout, export progress — the last two barely count as "components" at all, just text/ProgressView). **The short custom list is exactly two surfaces that have no first-party equivalent anywhere in the SDK: the scrubbable timeline/playhead and the Trim range selector** (both stem from the same gap: no first-party range- or position-over-a-timeline control exists in SwiftUI). The live level meter is a third, softer case — `Gauge`/`ProgressView` exist but don't model VU-meter semantics, so custom is the pragmatic call even though it's not as clear-cut an SDK gap as the other two.

## Menu bar extras

**Exactly three `MenuBarExtra` styles exist**, all declared at `@available(macOS 13.0, *)` (Ventura) with no changes found at 26.0 or 27.0 in either interface file:

| Style | Type | Citation |
|---|---|---|
| `.menu` (pull-down menu) | `PullDownMenuBarExtraStyle` | `SwiftUI.swiftinterface:8055` (struct), `:8078` (`.menu` static var) |
| `.window` (popover-like custom view) | `WindowMenuBarExtraStyle` | `SwiftUI.swiftinterface:5952` (struct), `:5975` (`.window` static var) |
| `.automatic` (system picks based on content) | `AutomaticMenuBarExtraStyle` | `SwiftUI.swiftinterface:21384` (struct), `:21407` (`.automatic` static var) |

`MenuBarExtra` itself (`SwiftUI.swiftinterface:2092`) is also unchanged since macOS 13. **There is no Liquid-Glass-era menu bar extra API** — no new style, no glass-specific modifier scoped to `MenuBarExtra` content. The menu bar itself is 24 pt tall on macOS (HIG, "The menu bar: Menu bar extras" — *"The menu bar's height is 24 pt"*), unchanged by Liquid Glass.

**HIG tension worth flagging explicitly**, since the map's plan and the HIG's stated preference point in different directions: the HIG's "Menu bar extras" page (`/design/Human-Interface-Guidelines/the-menu-bar#Menu-bar-extras`) says plainly — *"Display a menu — not a popover — when people click your menu bar extra. Unless the app functionality you want to expose is too complex for a menu, avoid presenting it in a Popovers."* This app's control panel (source picker with icons, start/stop, presumably a live level meter) is arguably "too complex for a menu" by the HIG's own escape clause, which is why `.window` (the popover-equivalent style) is the right call here — but it's a deliberate exception to a stated default, not the unmarked default, and worth recording as such if this becomes an ADR.

**Active/recording state.** There is no dedicated "menu bar extra state" API. The HIG's icon guidance (same page) says to *"consider using a symbol"* (an SF Symbol or custom template icon) and notes that both interface icons and symbols *"use black and clear colors to define their shapes; the system can apply other colors to the black areas... so it looks good on both dark and light menu bars, and when your menu bar extra is selected."* In practice, conveying "recording" is left entirely to the app: swap the `MenuBarExtra` label's `Image`/`Label` content based on state (e.g., a filled vs. outline SF Symbol, or a red-tinted variant — tinting breaks the monochrome template convention and should be used sparingly per that same guidance), or animate it (SwiftUI symbol effects — `.symbolEffect(.pulse)` etc. — apply to any `Image(systemName:)`, including one hosted in a `MenuBarExtra` label, since the label is just a normal SwiftUI view tree). **No official, state-varying or animated menu-bar-icon component exists** beyond "you control what view renders as the label" — this is a place where the app has full freedom but zero scaffolding.

## (c) Waveform rendering

**There is no first-party waveform or audio-visualization view anywhere in the macOS 27 SDK.** Verified by grepping (case-insensitive) for `waveform` across every relevant framework's Swift interface — `SwiftUI`, `SwiftUICore`, `AVFAudio`, `MediaPlayer`, `AVKit`, `Charts` — with zero matches in any of them. AVKit's entire macOS-visible SwiftUI surface is a single type: `VideoPlayer<VideoOverlay>` (`_AVKit_SwiftUI.framework/Versions/A/Modules/_AVKit_SwiftUI.swiftmodule/arm64e-apple-macos.swiftinterface:13`) — a video-frame player, not reusable for audio-only visualization, and AVKit's own top-level `AVKit.swiftmodule` interface is essentially empty (15 lines) on macOS, meaning its real surface is ObjC-only (`AVPlayerView` etc.), not SwiftUI-native.

**Sanctioned approach, assembled from what does exist:**

1. **Sample data**: `AVAudioFile` (declared in `AVFAudio.framework/Versions/A/Headers/AVAudioFile.h:29`, `API_AVAILABLE(macos(10.10), ...)`) is the standard way to pull PCM samples out of a recorded file for waveform analysis — `readIntoBuffer:frameCount:error:` (header line 141) into an `AVAudioPCMBuffer`, seeking via the `framePosition`/`length` properties (header lines 182, 189). macOS 27 adds a `Sendable`-friendly overload — `read(frameCount:) throws -> AVReadOnlyAudioPCMBuffer` — declared at `AVFAudio.swiftinterface:329`, gated `@available(macOS 27.0, iOS 27.0, tvOS 27.0, visionOS 27.0, *)` (`AVFAudio.swiftinterface:326`). For a long recording, don't read the whole file into memory: read in chunks and downsample (e.g., min/max or RMS per pixel-column) as you go. `AVAssetReader` (`AVFoundation.framework/Versions/A/Headers/AVAssetReader.h:63`) is the alternative entry point when reading via `AVAsset`/`AVAssetTrack` rather than a bare file URL; either is legitimate, `AVAudioFile` is the simpler one for a local file this app already owns.
2. **Drawing primitive**: `Canvas` (`SwiftUICore.framework` interface, `struct Canvas<Symbols>`) is the right fit — immediate-mode drawing via `GraphicsContext`, meant for exactly this kind of bulk custom rendering (thousands of `Path` segments or `stroke` calls per frame) without SwiftUI diffing each sample as a view. `Charts` (Swift Charts) exists on macOS with `LineMark`/`AreaMark`/`BarMark`/`PointMark` (`Charts.framework` interface lines 1942–2395) and *could* technically render a downsampled waveform as an `AreaMark` series, but it's a statistical-chart framework — each mark is a view-graph node, and Charts is not built or documented for tens of thousands of data points redrawn continuously; `Canvas` is the framework-appropriate choice for a scrubbing, possibly-live waveform. `Path`/`Shape` are the lower-level primitives `Canvas` composes internally; reach for a plain `Shape` only if the waveform is static and non-interactive.
3. **Performance note for long recordings**: downsample before drawing (min/max envelope per horizontal pixel is standard for waveforms — drawing one vertical line per sample is both wasteful and visually wrong past a few thousand samples), cache the downsampled envelope per zoom level rather than recomputing on every scrub, and do the `AVAudioFile` read/downsample work off the main actor since `Canvas`'s `GraphicsContext` drawing itself must stay on the main thread but the data prep does not.

## What is new in macOS 27 SwiftUI this app should use

Cross-checked against the SDK (not just the skill summary — see the corrections below).

- **`PickerStyle.tabs` / `TabsPickerStyle`** — new at `@available(iOS 27.0, macOS 27.0, tvOS 27.0, visionOS 27.0, *)` (`SwiftUI.swiftinterface:16647,16653`). A genuine fit for the Quality Preset picker.
- **`EnvironmentValues.appearsActive`'s new macOS-27 backing** (§a) — free, automatic inactive-window dimming for the editor window; nothing to write beyond reading the environment value if a custom control wants to dim itself when the window isn't key.
- **`ToolbarItemVisibilityPriority` / `ToolbarContent.visibilityPriority(_:)`** — usable on macOS, but note it's actually `@available(iOS 27.0, macOS 26.1, ...)` (`SwiftUI.swiftinterface:13396`, `13394`) — a **macOS 26.1** addition, not 27. Worth using if the editor toolbar gets tight, but it predates this OS.
- **Correction to the "toolbar overflow" story for this app**: the swiftui-whats-new-27 skill and the WWDC session both describe new toolbar-overflow machinery, but on macOS specifically most of it doesn't apply — `ToolbarOverflowMenu` is `@available(iOS 27.0, visionOS 27.0, *)` with an explicit `@available(macOS, unavailable)` (`SwiftUI.swiftinterface:31417-31420`), and `ToolbarItemPlacement.topBarPinnedTrailing` is likewise `@available(iOS 27.0, visionOS 27.0, *)` / `@available(macOS, unavailable)` (`SwiftUI.swiftinterface:7801,7806`). Given this app is a single MenuBarExtra plus one small editor window (not a NavigationSplitView or TabView-heavy app), none of the reorderable-list, tab-bar-minimize, or document-package machinery introduced in 27 (`reorderable()`/`reorderContainer`, `TabBarMinimizeBehavior`, `Document`/`DocumentGroup(makeReadableDocument:)`) has an obvious application here — the app has no reorderable list, no `TabView`, and Recordings are auto-saved rather than user-managed documents opened via `DocumentGroup`.
- **Automatic Liquid Glass propagation** (§a) is the one big "don't hand-roll" item: stock `Button`, `Picker`, `Slider`, `Toggle`, and window chrome pick up the current Liquid Glass tint automatically on rebuild — no version check, no opt-in modifier, so long as custom controls stay on official components per this app's standing preference.

## What I could not verify

- **The SDK path in the ticket doesn't exist on this machine.** The ticket specifies `/Applications/Xcode.app/...`; only `/Applications/Xcode-beta.app` is installed. I used the beta's SDK (confirmed `macOS 27.0` via `SDKSettings.plist`), which should be the same SDK content, but I could not cross-check against a non-beta Xcode 27 install since none exists here.
- **Whether `NSLevelIndicator` is actually usable for smooth, high-frequency level-meter updates** (vs. its apparent design purpose of discrete/static capacity readouts) is an inference from its header documentation and API shape, not something I tested or found explicitly confirmed/denied in the HIG or API docs. Flagged as "not proven either way" in the table above rather than asserted.
- **Whether "iPad and Mac Menu Bars now have a minimal set of icons by default" (WWDC26 session 269)** applies to `MenuBarExtra` status items or only to an app's own File/Edit/View command menus. The transcript excerpt and the `labelStyle(.titleAndIcon)` example it pairs with both read as being about in-app `Commands`/menu items, not the systemwide `MenuBarExtra` icon — I did not find a HIG or API passage that ties this specifically to `MenuBarExtra`, so I did not include it as a menu-bar-extra finding above. Worth a second look if the editor window ends up with a custom `CommandGroup`.
- **No third-party source was used as a citation** — MacRumors/AppleInsider/TechRadar/Cult of Mac pieces on macOS 27's Liquid Glass tint slider were read only as leads and cross-referenced against the WWDC26 session 269 page and the SDK; where I couldn't find first-party confirmation of a specific claim (e.g. the exact wording "ported across all system icons"), I left it out rather than cite the secondary source.
- **`AVAssetReader` was confirmed to exist** (header path only) but I did not read its full API surface — `AVAudioFile` was sufficient to answer the sample-data question for a local recording, so I didn't need to characterize `AVAssetReader` in depth.
