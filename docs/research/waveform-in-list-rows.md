# What should AppTape's per-row audio indicator be, on macOS 27?

Research for the menu bar panel's app list: each row needs a minimal, live indicator of "is this app making sound, and how loud," which must give way to a Record button on hover. Every claim below is either (a) a `file:line` + exact `@available`/`API_AVAILABLE` annotation read directly from the installed macOS 27.0 SDK, (b) a quoted passage from Apple Developer Documentation fetched via `mcp__xcode__DocumentationSearch`, or (c) explicitly flagged as observed OS behavior or my own inference. This machine: Xcode 27.0 at `/Applications/Xcode-beta.app` (no `/Applications/Xcode.app` here), macOS 27.0 build 26A5416b confirmed via `sw_vers`. SDK root (`$SDK` below):

```
/Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk
```

Interfaces read in full or by targeted grep, all under `$SDK/System/Library/Frameworks/`:
`SwiftUI.framework/Modules/SwiftUI.swiftmodule/arm64e-apple-macos.swiftinterface` (34,178 lines), `SwiftUICore.framework/Versions/A/Modules/SwiftUICore.swiftmodule/arm64e-apple-macos.swiftinterface` (27,574 lines), `Symbols.framework/Modules/Symbols.swiftmodule/arm64e-apple-macos.swiftinterface` (637 lines, read in full). This builds on `docs/research/design-language.md` (already established in this repo: no first-party waveform view anywhere in the SDK; `Gauge`'s `.circular`/`.linear` styles are `@available(macOS, unavailable)`; Liquid Glass's public API shipped at macOS 26.0 and did not grow at 27.0).

## Recommendation

**The row's persistent indicator should be `Image(systemName: "speaker.wave.3", variableValue: level)` — a static, value-driven fill, not a continuously-animating `SymbolEffect` — reserving `.symbolEffect(.variableColor.iterative, isActive:)` only for a brief "just started/stopped" transition, not perpetual looping per row.** This is a deliberate departure from the SF Symbols "Animations" HIG page's suggestion, and the reasoning is in §3: continuous per-row looping animation in a list is exactly what the HIG's own general Motion guidance and Apple's frame-rate/energy guidance argue against, even though `variableColor` is documented as the idiomatic *symbol* for "playback, connecting, or broadcasting." `variableValue` alone, redrawn once per level update (a few times a second, driven by your own tap callback — not a `TimelineView` running at animation cadence), gives a live, legible, cheap readout without a perpetually-animating list. If product wants more liveliness than a value-driven fill provides, `.breathe` is Apple's own named idiom for "an ongoing recording session" (§1) and is the second-best choice — but audit it against Reduce Motion and the energy guidance in §3 before shipping it as a default-on, always-running per-row animation. **On hover, replace the indicator with a `Button` (`record.circle` / a red dot) via `.onHover(perform:)` toggling local state** — there is no first-party "swap content on hover" component on macOS (`HoverEffect` and `listRowHoverEffect` are both `@available(macOS, unavailable)`, §6) — `.onHover` plus a conditional view and a short `.animation`/`.contentTransition` cross-fade is the only idiomatic path, and it matches the long-standing macOS convention of a row swapping a passive glyph for an action control on hover (observed behavior, e.g. Music's track-number↔play-button swap — not a documented HIG pattern, see §6).

**This recommendation assumes a continuous `level` value is available to feed `variableValue` — and that assumption itself has a real gate.** A parallel session in this repo (`prototype/source-picker`, currently at commit `766ab5c` "Prototype three source-picker variants against live HAL data") reported the following via task instruction, from live testing on this machine — **not independently reproduced or verified by this research pass**, and outside this document's SwiftUI/HIG scope (it belongs with `docs/research/capture-api.md` / `docs/research/tcc-permissions.md`): simultaneous Core Audio process taps on two apps stayed correctly isolated per-process (Chrome varying 0.57–0.75 on real content; QuickTime holding a constant 0.3662 on a pure 440 Hz tone), so true per-app amplitude is achievable in principle — but only once that tap's TCC recording-permission grant is held. An ungranted tap reportedly doesn't error: `AudioDeviceStart` returns `noErr` while the tap silently yields zero samples, and there is reportedly no API to query grant status ahead of starting a tap. Taking that as given (with the unverified caveat above), the indicator design splits into two cases:

- **(a) No grant held — the common case, before the user has asked to record anything.** No row can safely open a tap just to populate a list indicator without prematurely surfacing the permission prompt. The indicator can only be as good as whatever tap-free signal is available (e.g. a coarse per-process "is this app producing audio at all" boolean, if one exists — not established by this document; see "What I could not verify"). Render that as a fixed two-state `variableValue` (0 or 1: silent vs. active), never a smooth level, and don't animate it beyond the one-shot state-change effect already recommended above.
- **(b) Grant held — e.g. a tap is already running because the user started recording that row, or after some one-time consent flow.** The full continuous `variableValue` fill described above applies, fed by that row's real tap callback.

In neither case should AppTape open a Core Audio tap per row just to light up the list: that would both re-trigger the premature-permission-prompt problem in (a) and repeat the N-simultaneous-effects performance caution already raised in §4/§5.

**No `SymbolEffect` is new at macOS 27.0.** The newest additions in the installed SDK are `.drawOn`/`.drawOff` at macOS 26.0 (SF Symbols 7-era "draw along a path" effects, for progress/directional meaning per the HIG text below — not level-related). This matches the repo's established finding that Liquid Glass and the surrounding symbol/animation vocabulary landed at 26 and did not expand at 27.

**Which effect is Apple's own idiom for "audio playing right now"?** Two separate, both documented, both directly on point:

- **`variableColor`** is the HIG's literal audio-level example. "SF Symbols: Variable color" (`/design/Human-Interface-Guidelines/sf-symbols#Variable-color`): *"you could use variable color with the `speaker.wave.3` symbol to communicate three different ranges of sound... by mapping the layers that represent the curved wave paths to different ranges of decibel values."* The companion "SF Symbols: Animations" page (`/design/Human-Interface-Guidelines/sf-symbols#Animations`) reinforces it under Variable color: *"You might use variable color to communicate progress or ongoing activity, such as playback, connecting, or broadcasting."*
- **`breathe`** is the HIG's literal *recording* idiom, and is arguably the more on-point choice for AppTape specifically: *"You might use the breathe animation to convey status changes, or signal that an activity is taking place, like an ongoing recording session. Breathe is similar to pulse; however pulse animates by changing opacity alone, while breathe changes both opacity and size to convey ongoing activity."* (same page, Breathe section). No other effect's HIG description names "recording."

**`variableValue` — the non-animated, value-driven path.** `Image(systemName:variableValue:)` and its siblings are declared at `SwiftUICore.swiftinterface:11243` (`@available(iOS 16.0, macOS 13.0, tvOS 16.0, watchOS 9.0, *)`), inits at `:11249-11253`. This is old (macOS 13, Ventura) — not new to 26/27. It is **not an animation**: passing a `Double` in `0...1` statically selects how many of a symbol's variable-color layers are filled, redrawn like any other SwiftUI state change. For `speaker.wave.3` that's a discrete 4-state fill (0 waves, 1, 2, 3), confirmed by the same HIG diagram cited above ("four versions of the speaker wave three symbol... zero, one, two, and three"). Feeding it a smoothed RMS/peak value from your own tap callback gives a live, cheap, legible level readout with zero perpetual-animation cost.

**Composing them.** None of the `SymbolEffect`s themselves take a continuous external value — `.symbolEffect(_:options:isActive:)` (indefinite effects, `SwiftUICore.swiftinterface:16513`) takes only a `Bool`, and `.symbolEffect(_:options:value:)` (discrete effects, `:16518`) takes an `Equatable` that triggers one **discrete replay** per change, not a continuous scrub. (Both are `@available(macOS 14.0, iOS 17.0, tvOS 17.0, watchOS 10.0, visionOS 1.0, *)`; both also carry `@_originallyDefinedIn(module: "SwiftUI", macOS 27.0)` at `SwiftUICore.swiftinterface:3305-3311` — an ABI relocation from `SwiftUI` into `SwiftUICore` at 27, not a new capability.) So **"a live meter" is only achievable by combining `variableValue` (the level) with an effect used sparingly as a state-change cue (isActive toggling on start/stop)** — there is no single `SymbolEffect` that reads as a true continuously-driven meter; every effect is a pre-authored animation curve, and asking one to loop forever is exactly the perpetual-motion pattern §3's guidance pushes against for lists.

**Legibility at Caption/Footnote size, and `.dimInactiveLayers`/`.hideInactiveLayers` at small sizes:** **not verified.** Neither the SF Symbols HIG pages nor `DocumentationSearch` returned any statement about animation legibility at small symbol scales. The "SF Symbols: Weights and scales" page (`/design/Human-Interface-Guidelines/sf-symbols#Weights-and-scales`) documents three *static* scales (small/medium/large) relative to SF Pro cap-height, but says nothing about `variableColor.iterative`/`.cumulative`/`.dimInactiveLayers` at those scales, and nothing about the SF Symbols app itself (which is where per-symbol animation-layer authoring is verified) was reachable from this sandbox. Treat any claim that these effects "still read clearly at caption size" as untested product-side.

## 2. Where Apple itself does this

The clean documented finding is above (§1: variableColor and breathe, named explicitly by the SF Symbols HIG). For **first-party UI precedent** — Now Playing / Control Center, Music's row, Safari's tab glyph, Voice Memos, Sound Settings' input meter — `DocumentationSearch` returned **no HIG or API-reference passage describing any of these surfaces' visual implementation**; Apple does not document the internals of its own system chrome this way. Everything below this line is either a documented *general-purpose component* (which I can cite) or observed/general knowledge about those specific surfaces (which I flag as such, and did **not** re-verify with a live screenshot on this machine this session — deliberately: this is the user's actual logged-in Mac (Apple M2 Pro, an attached display), and driving its GUI to open System Settings/Safari for a screenshot risked disrupting an active session for a documentation-adjacent question, so I did not do it).

- **The closest thing to a *documented* answer is the "Gauges: macOS" HIG page** (`/design/Human-Interface-Guidelines/gauges#macOS`), which names and describes exactly the segmented-LED visual language a VU/input meter uses, as a **Discrete capacity indicator**: *"A horizontal row of separate, equally sized, rectangular segments. The number of segments matches the total capacity, and the segments fill completely — never partially — with color to indicate the current value."* Its Continuous sibling is *"a horizontal translucent track that fills with a solid bar."* Both are backed by a real, citable AppKit control: `NSLevelIndicator` (`AppKit.framework/Versions/C/Headers/NSLevelIndicator.h:25`, `API_AVAILABLE(macos(10.10))`, per `docs/research/design-language.md`; the HIG's own "Gauges: Developer documentation" section links `NSLevelIndicator` directly). This is the vocabulary System Settings' Sound → Input meter has used for many macOS versions (observed/general knowledge, not reverified this session) — the HIG documents the *shape* of that idiom without naming the specific system surface.
- **Safari's "playing audio" tab glyph, Control Center/menu-bar Now Playing, and Voice Memos' list row**: general, long-standing observed macOS/iOS behavior, not independently reconfirmed on this build — Safari shows a small static speaker glyph in a tab that is producing audio (click to mute), Control Center's Now Playing widget shows artwork plus transport controls with no live waveform, and Voice Memos' *list* of past recordings shows a static duration/thumbnail rather than a live trace (its live waveform belongs to the *active recording* screen, not a list row). I did not verify any of these against macOS 27.0 specifically in this session.
- Two adjacent HIG pages worth citing for completeness even though they don't answer the row-indicator question directly: **"Playing audio: macOS"** (`/design/Human-Interface-Guidelines/playing-audio#macOS`) is a single sentence — *"In macOS, notification sounds mix with other audio by default"* — and has nothing about level meters. **"Sliders: iOS, iPadOS"** (`/design/Human-Interface-Guidelines/sliders#iOS-iPadOS`) explicitly steers volume UI toward a "volume view" rather than a slider, but that guidance is scoped to iOS/iPadOS and to *output-volume control*, not a per-app *input/activity* readout — not directly transferable.

**Bottom line for this question:** there is a documented visual vocabulary for a level meter (`NSLevelIndicator`'s discrete/continuous styles, "Gauges: macOS") and a documented symbol idiom for "sound is happening" (`variableColor`) and for "recording is happening" (`breathe`) — but no first-party text describing which one Apple's own apps actually pick for a *list row* specifically. That choice is left to the app, which is itself consistent with the design-language.md finding that menu-bar/list "active state" is entirely uninstrumented territory in the SDK.

## 3. Motion rules

**No HIG page dedicated to "continuous animation in lists/menus" exists** — searches for lists-and-tables motion guidance, menu-bar motion, and general motion pages turned up only the platform-agnostic **"Motion: Best practices"** and **"Motion: Providing feedback"** pages, plus the SF Symbols Animations page cited in §1. Reading them together produces a real tension, not a clean rule:

- **Against perpetual per-row animation:** *"In apps, generally avoid adding motion to UI interactions that occur frequently. The system already provides subtle animations for interactions with standard interface elements. For a custom element, you generally want to avoid making people spend extra time paying attention to unnecessary motion every time they interact with it."* (Motion: Providing feedback, `/design/Human-Interface-Guidelines/motion#Providing-feedback`). And: *"Add motion purposefully, supporting the experience without overshadowing it. Don't add motion for the sake of adding motion."* (Motion: Best practices, same page family, `#Best-practices`) — a list of N rows each running its own indefinite `SymbolEffect` forever is close to the textbook case this is warning about.
- **For it, narrowly:** the SF Symbols Animations page explicitly sanctions `variableColor`/`breathe`/`pulse` for exactly "ongoing activity" (§1) — Apple's own idiom is *not* motion-on-change, it's continuous-while-active. My reading: **the HIG's caution is about gratuitous or decorative motion on interactions that recur often (e.g., re-animating on every click), not about a state-driven "this is currently true" indicator** — but nothing I found states that distinction explicitly for lists. Treat the recommendation in this doc's headline (value-driven `variableValue`, animation reserved for state transitions) as **my inference** reconciling these two pages, not a quoted rule.

**`accessibilityReduceMotion` / degrade path.** `EnvironmentValues.accessibilityReduceMotion` is old — `SwiftUICore.swiftinterface`, declared in the extension block headed `@available(iOS 13.0, macOS 10.15, tvOS 13.0, watchOS 6.0, *)` (property itself at line `23466`), unchanged at 26/27. The concrete API to gate a symbol effect on it is `.symbolEffectsRemoved(_:)` — `SwiftUI.swiftinterface:3315`, `@available(macOS 14.0, iOS 17.0, tvOS 17.0, watchOS 10.0, *)` — apply as `.symbolEffectsRemoved(reduceMotion)`. Because `variableValue` is a static state, not an animation, it needs no gating at all; only a wrapped `SymbolEffect` (breathe/variableColor/pulse) does. The HIG's **"Accessibility: Cognitive"** page (`/design/Human-Interface-Guidelines/accessibility#Cognitive`) gives the concrete degrade checklist for when Reduce Motion is on: *"reducing automatic and repetitive animations, including zooming, scaling, and peripheral motion... Tightening animation springs to reduce bounce effects... Replacing transitions in x-, y-, and z-axes with fades to avoid motion."* For this indicator specifically: drop straight to the static `variableValue` fill.

**`accessibilityDimFlashingLights` is very likely the wrong lever here.** It's declared `@available(macOS 14.0, iOS 17.0, tvOS 17.0, watchOS 10.0, *)` (extension block above `SwiftUICore.swiftinterface:23519`, `_originallyDefinedIn` macOS 15.0). The HIG's own framing (**Accessibility: Cognitive**) is about *"bright, frequent flashes of light in the media they consume"* — video-playback strobing, not a slow opacity pulse on a small glyph. I found nothing suggesting Apple expects `SymbolEffect` usage to be gated on this value; `accessibilityReduceMotion` is the one that matters for this indicator. This is my inference from the documented scope of each flag, not a stated rule pairing them.

**Refresh-rate / energy guidance for a continuously-animating menu-bar item.** Nothing macOS-specific or `MenuBarExtra`-specific was found. The closest first-party guidance is written for iOS/iPadOS ProMotion but states general, transferable principles: **"Improving your app's rendering efficiency: Limit the frame rate and duration of animations"** (`/documentation/Xcode/improving-your-app-s-rendering-efficiency#Limit-the-frame-rate-and-duration-of-animations`) — *"Higher frame rates cause the system to use more power"* — and **"Optimizing iPhone and iPad apps to support ProMotion displays: Provide timing hints to Core Animation"** (`/documentation/QuartzCore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays#Provide-timing-hints-to-Core-Animation`), whose frame-rate table explicitly classifies "Small, low-speed animations" — its own examples are *"Clock ticking; progress bar"*, directly analogous to a per-row level readout — into an 8–24 Hz tier, versus 80–120 Hz reserved for "High-impact animations... used sparingly to minimize power consumption." I'm citing this as the closest available first-party energy principle, **not** as macOS- or `MenuBarExtra`-specific guidance — no such page exists in what I could reach. The practical translation for AppTape: update the `variableValue` level a few times a second from your own audio-tap callback (not on every render frame), and if any `SymbolEffect` is used at all, keep it to the shortest indefinite loop that still reads as "active," not a fast/high-fidelity animation.

## 4. The `Canvas` path, if a symbol is not enough

For a custom 3–5-bar mini-waveform (~16 pt tall), the idiomatic macOS 27 drivers, all confirmed present with **no new overloads at macOS 26.0/27.0** (each identifier below was located via an exhaustive grep of both interfaces, and every hit is shown):

- **`TimelineView`** — `SwiftUI.swiftinterface:29445` (struct), `@available(iOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, *)`.
- **`.animation(minimumInterval:paused:)`** — exists exactly as the task asked: `TimelineSchedule.animation(minimumInterval:paused:)`, `SwiftUI.swiftinterface:11229-11238`, `AnimationTimelineSchedule` struct at `:11239`, both `@available(iOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, *)`. This is the throttle mechanism the task asked about, and it has existed since macOS 12 (Monterey) — not new.
- **`withAnimation(_:_:)`** — `SwiftUICore.swiftinterface:22304`, `@available(iOS 13.0, macOS 10.15, tvOS 13.0, watchOS 6.0, *)` — SwiftUI's original imperative-animation entry point.
- **`.phaseAnimator(_:content:animation:)`** (auto-cycles repeatedly with no `trigger:`) and **`.phaseAnimator(_:trigger:content:animation:)`** (replays once per value change) — `SwiftUICore.swiftinterface:18179,18187`, both `@available(iOS 17.0, macOS 14.0, tvOS 17.0, watchOS 10.0, *)`.
- **`.keyframeAnimator(initialValue:trigger:content:keyframes:)`** and **`...repeating:content:keyframes:`** — `SwiftUICore.swiftinterface:2877,2880`, both `@available(iOS 17.0, macOS 14.0, tvOS 17.0, watchOS 10.0, *)`.
- **`Canvas`** — `SwiftUICore.swiftinterface:22244` (struct), `@available(iOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, *)`.

None of these six identifiers produced a single additional `@available(macOS 26...)` or `@available(macOS 27...)` overload anywhere in either interface — every occurrence of each name in the file is the one cited above.

**Cost of N rows animating at once, and the `Canvas`-vs-`HStack` question.** No first-party document addresses "many simultaneously-animating list rows" directly. Two adjacent, real considerations:

1. **`List` is already lazy** — off-screen rows aren't instantiated (this is `List`'s whole reason to exist over a plain `VStack`; see the general performance framing in **"Creating performant scrollable stacks: Consider lazy stacks for large numbers of views"**, `/documentation/SwiftUI/Creating-Performant-Scrollable-Stacks#Consider-lazy-stacks-for-large-numbers-of-views`). So "N rows animating" is bounded by rows actually visible in a small popover-style panel — likely under ~15 — not the full running-app count. This matters for both this question and the Liquid Glass performance warning in §5, which is explicitly about *simultaneous onscreen* effects.
2. **At 3–5 bars and ~16 pt, `Canvas`'s `GraphicsContext` is the wrong tool; a plain `HStack` of `Capsule`s with `.scaleEffect(y:)` is the better fit.** `Canvas` exists to avoid SwiftUI's per-view diffing cost when drawing hundreds/thousands of primitives in one immediate-mode pass (the sanctioned tool for the *static, full-recording* waveform this repo already established — `docs/research/design-language.md`'s §c). Five `Capsule` views is nowhere near that threshold; SwiftUI's own view-diffing overhead for five small shapes per row is negligible next to the bookkeeping `Canvas` would add for no benefit, and plain shapes are far easier to drive per-bar from a `phaseAnimator`/`withAnimation` and to gate individually behind Reduce Motion. This is my inference/recommendation, not a documented rule — I found no HIG or API text that states a size/count threshold for choosing `Canvas` over composed `Shape` views.

## 5. Liquid Glass and lists specifically

Building on this repo's established finding (`docs/research/design-language.md`): every glass-specific SwiftUI type is `@available(macOS 26.0, *)` or later, none new at 27.

**Does a row's live indicator count as functional or content?** By the HIG's own definitions, the row is **content** (each row *is* a piece of data — a running app — not chrome or navigation), and the indicator is a passive readout of that content's state, not a control: *"Don't use Liquid Glass in the content layer... use Standard materials for elements in the content layer, such as app backgrounds. An exception is for controls in the content layer with a transient interactive element like Sliders and Toggles; in these cases, the element takes on a Liquid Glass appearance to emphasize its interactivity when a person activates it."* (**"Materials: Liquid Glass"**, `/design/Human-Interface-Guidelines/materials#Liquid-Glass`). The exception is explicitly for *interactive* transient controls, and a passive level readout doesn't qualify — so **the indicator itself should not carry glass.** The hover-revealed **Record button**, by contrast, *is* a real interactive control; a stock `Button` picks up `buttonStyle(.glass)`/`.glassProminent` automatically per the same page family (already cited in design-language.md), so it can legitimately glass itself as a system-standard control without you doing anything — that's consistent with the "functional layer" reading, not a contradiction.

**Glass inside a scrolling `List`, specifically, or `MenuBarExtra` `.window` panel selection appearance: no dedicated HIG or API text found for either.** Searches for list row backgrounds, scroll-view/list glass caveats, and `MenuBarExtra` panel selection returned nothing on point beyond the general performance warning already established in design-language.md and repeated here because it directly bears on "one indicator per row": **"Applying Liquid Glass to custom views: Optimize performance when using Liquid Glass effects"** (`/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views#Optimize-performance-when-using-Liquid-Glass-effects`) — *"Creating too many Liquid Glass effect containers and applying too many effects to views outside of containers can degrade performance. Limit the use of Liquid Glass effects onscreen at the same time."* Giving each of N rows its own `glassEffect`/`GlassEffectContainer` is precisely the pattern this warns against — one more reason (independent of the content-layer argument above) to keep the row's own background and indicator on the standard-materials/no-material path, and reserve glass for the panel's outer chrome and the hover Record button.

**`backgroundExtensionEffect()`** — `SwiftUI.swiftinterface:15832`, `@available(macOS 26.0, iOS 26.0, tvOS 26.0, watchOS 26.0, visionOS 26.0, *)` — exists (already noted in design-language.md) but is for extending background *imagery* under bars/edges; no documented or plausible use inside a list row, and I found no source connecting it to `List` at all.

**Selection appearance in a `.window`-style `MenuBarExtra` panel:** nothing documented specifically. `List` selection on macOS inherits the platform's standard accent-color highlight by default; no source found describing whether/how that changes inside a `MenuBarExtra(.window)` panel versus a normal window. Treat as an open question to verify empirically (prototype), not something resolvable from documentation.

## 6. Spacing and sizing

**Numeric metrics found, all carried over from `docs/research/design-language.md`'s citations (re-verified as still the relevant numbers, not re-derived independently here):**

- macOS default control size **28×28 pt**, minimum **20×20 pt** (HIG "Designing for games" cross-platform table, `#Look-stunning-on-every-display`) — the natural size band for the trailing accessory, whichever of the indicator/button is showing.
- macOS built-in text styles (HIG Typography, `#macOS-built-in-text-styles`): **Caption 1 & 2 — 10/13 pt** (size/line-height), **Footnote — 10/13**, **Subheadline — 11/14**, **Body — 13/16**. A title/subtitle pair in a compact row should sit at Body-over-Caption or Subheadline-over-Footnote, not an invented size.
- A general (non-List-specific) HIG spacing rule with a hard number: **"Eyes: Making items easy to see"** (`/design/Human-Interface-Guidelines/eyes#Making-items-easy-to-see`) — *"you can help ensure that there's enough space between interactive items by using a margin of at least 16 points around the bounds of each item or by placing items so that their centers are always at least 60 points apart."* This is cross-platform, not List-specific, but it's the only sourced numeric floor for spacing near an interactive element (the hover Record button) that I found.

**No documented numeric default for macOS `List` row height, nor for a trailing-accessory inset, exists in either the SDK or the HIG text I could reach.** `EnvironmentValues.defaultMinListRowHeight` and `defaultMinListHeaderHeight` are real, documented environment keys (`/documentation/SwiftUI/Lists#Configuring-a-lists-layout`), but their *default numeric values* are not published anywhere I could find — the doc page states what the keys are for, not their default points. `listRowInsets(_:)` similarly has no documented default numeric inset. This is a genuine gap, not an oversight on my part — flagged again below.

**Standard idiom for a row with BOTH a persistent status indicator AND a hover-revealed action button: there is no first-party SwiftUI component for this on macOS, and the closest-sounding APIs are explicitly unavailable there.**

- `HoverEffect` (`.automatic`/`.highlight`/`.lift`, driving `.hoverEffect(_:)`) — the struct itself is `@available(iOS 13.4, tvOS 16.0, *)` with an explicit `@available(macOS, unavailable)` (`SwiftUICore.swiftinterface:2276-2280`). This entire system (built for touch/remote/gaze hover) does not exist on macOS.
- `listRowHoverEffect(_:)` / `listRowHoverEffectDisabled(_:)` — `SwiftUI.swiftinterface:3066,3072,3074`, `@available(visionOS 1.0, *)` with an explicit `@available(macOS, unavailable)`. visionOS-only (gaze-hover on a `List` row).
- `.onHover(perform: (Bool) -> Void)` — `SwiftUI.swiftinterface:8244`, `@available(iOS 13.4, macOS 10.15, *)` (`tvOS`/`watchOS` unavailable). **This is the one macOS-available primitive**, and has been since Catalina.

So the idiomatic macOS 27 pattern is: `.onHover(perform:)` toggling a local `@State var isHovering: Bool`, with the row's trailing accessory conditionally showing the indicator or the Record `Button`, wrapped in a short `withAnimation`/`.contentTransition` for the swap. This mirrors a real, long-standing macOS convention — a row swapping a passive glyph (track number, file-size text, a status dot) for an action control (a Play button, a checkbox) on hover, seen for many years in Music/iTunes and Finder — but that pattern is **observed behavior**, not something the HIG documents by name anywhere I found; the "Lists and tables" HIG pages (both the general page and its `#macOS` section) describe column sorting, resizing, alternating-row colors, and outline views, but say nothing about a hover-swap trailing accessory.

## What I could not verify

- **Whether any individual SF Symbol name (`waveform`, `speaker.wave.3`, etc.) actually supports `variableColor`/`variableValue` layers, beyond the one HIG diagram example (`speaker.wave.3`).** Per-symbol variable-color layer support is authored data inside the SF Symbols app, not something `DocumentationSearch` or the SDK interfaces expose; I did not have access to the SF Symbols app in this environment.
- **Animation legibility of `variableColor`/`breathe`/`pulse` at Caption/Footnote symbol scale.** No HIG or API text addresses this; my headline recommendation to prefer a static `variableValue` fill over a perpetually-animating effect is partly motivated by this unknown, not just by the motion/energy reasoning in §3.
- **How Apple's own apps actually render Safari's tab-audio glyph, Control Center/menu-bar Now Playing, Voice Memos' row, and Sound Settings' input meter on macOS 27.0 specifically.** I deliberately did not take a live screenshot of this machine's running desktop to check (see §2) — everything stated about these surfaces is general/observed knowledge, not reconfirmed this session, and should be treated as a lead to verify empirically before committing to it in a spec or ADR.
- **List row selection appearance and any glass behavior inside a `MenuBarExtra(.window)` panel specifically.** No documentation found either way; §5 flags this as an open question needing a small prototype.
- **Documented default numeric values for `defaultMinListRowHeight`, `defaultMinListHeaderHeight`, and default `listRowInsets` on macOS.** The environment keys and modifiers are documented as concepts; their actual default point values are not published anywhere I could reach.
- **Whether `accessibilityDimFlashingLights` is genuinely irrelevant to a slow SF Symbol pulse**, versus `accessibilityReduceMotion` being the sole relevant flag. My read (§3) is an inference from each flag's documented scope (video-strobing vs. general motion), not a stated rule connecting or excluding either from `SymbolEffect` usage.
- Did not build or run any code against this SDK to confirm frame-pacing, CPU, or battery cost empirically for either the `SymbolEffect` or `Canvas`/`TimelineView` paths — this is a documentation/header-research task, not a prototype spike. A short prototype (per the repo's `prototype` skill) is the natural next step before locking in the indicator's implementation, especially for the N-simultaneous-rows question in §4 and the hover-swap interaction in §6.
- **The Core Audio process-tap findings in the Recommendation's addendum** (per-process amplitude isolation between two simultaneously-tapped apps; an ungranted tap returning `noErr` with silent zero samples instead of erroring; no API to query grant status ahead of a tap) — reported via task instruction from a parallel `prototype/source-picker` session on this machine, not independently reproduced against Core Audio headers/documentation or re-verified by this research pass. Treat as a lead corroborated only by that branch's commit history (`766ab5c`, "Prototype three source-picker variants against live HAL data"), not as a sourced fact of this document.
- **Whether a tap-free, boolean "is this app currently producing audio" signal exists on macOS 27** for the no-grant case in the Recommendation's addendum (e.g. via a non-tap Core Audio API, `NSRunningApplication`, or some other lower-trust source). Not investigated here — out of this document's SwiftUI/HIG scope; belongs with `docs/research/capture-api.md` / `docs/research/tcc-permissions.md`.
