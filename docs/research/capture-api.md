# Which API captures one chosen app's audio on macOS 27?

Research for [issue #2](https://github.com/SamWongML/macos-audio-recording/issues/2), part of the [map](https://github.com/SamWongML/macos-audio-recording/issues/1). Constraints carried over from the map: macOS 27.0 only, local-run only (no notarization/sandbox/App Store), must not require a virtual audio driver.

**SDK used for header inspection**: this machine has Xcode 27.0 (build 27A5237l) installed at `/Applications/Xcode-beta.app`, not the `/Applications/Xcode.app` path the ticket assumed — that path does not exist here. Headers below are read from `/Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk` (also present as `MacOSX27.sdk` / `MacOSX27.0.sdk`), running on macOS 27.0 (build 26A5416b, per `sw_vers`).

## Recommendation

**Use Core Audio process taps** (`AudioHardwareCreateProcessTap` + `CATapDescription`, read through an aggregate device via `AudioDeviceCreateIOProcIDWithBlock`). Reject ScreenCaptureKit for this job.

Decisive reasons:

1. It is the only one of the two that is actually an **audio primitive**. ScreenCaptureKit is a screen-capture API that happens to also carry audio — Apple's own `SCStreamConfiguration`/`SCContentFilter` design and its own official sample project always attach a `.screen` stream output, and an Apple Developer Forums thread from a developer who tried to get audio-only output from `SCStream` was told directly by the community, with the original poster accepting it: for macOS 14.2+, "you can use `AudioHardwareCreateProcessTap`... (but it isn't ScreenCaptureKit)" ([forum thread 718279](https://developer.apple.com/forums/thread/718279)).
2. It uses a **narrower, better-fitting TCC permission**: "System Audio Recording" only, versus ScreenCaptureKit's "Screen Recording" (now "Screen & System Audio Recording"). Apple's own sample documentation for ScreenCaptureKit states plainly: "The first time you run this sample, the system prompts you to grant the app Screen Recording permission. After you grant permission, you need to restart the app to enable capture" (Apple Developer Documentation, "Capturing screen content in macOS: Configure the sample code project", via `mcp__xcode__DocumentationSearch`). A forced-restart, screen-shaped permission prompt is a poor first-run experience for a menu-bar app whose only ask is "let me hear what Chrome is playing."
3. It is **genuinely per-process at the HAL level**, and macOS 26+ (in scope, since the app targets 27.0) added exactly the primitives this app needs for multi-process browsers: tap by `bundleIDs` array and `processRestoreEnabled` to reattach a tap automatically as matching processes come and go (`CATapDescription.h`, both marked `API_AVAILABLE(macos(26.0))` — see citations below). This is the most decision-relevant fact found in this research and it did not exist before macOS 26.
4. No virtual audio driver in either candidate — not a differentiator, but confirmed for both (see below).

This is **not risk-free** — see "What I could not verify" and the open bugs cited under Core Audio taps. The map's own "Not yet specified" item, *"Behaviour when the Source quits, changes output device, or changes sample rate mid-Recording"*, cannot be closed by this ticket alone; it needs a prototype spike against real Chrome/Safari sessions before that behavior is locked into the spec.

## The field is only these two APIs

Checked directly against the installed macOS 27.0 SDK, not assumed:

- `grep -rl "CATapDescription\|AudioHardwareCreateProcessTap"` across every framework in `MacOSX.sdk/System/Library/Frameworks/` matches only `CoreAudio.framework` (`AudioHardware.h`, `AudioHardwareTapping.h`, `CATapDescription.h`, and the module map/tbd). No other framework references these symbols.
- `AVFAudio.framework/Headers/` (34 headers) and `AVFoundation.framework/Headers/` were grepped for `processTap|ProcessAudio|SystemAudio|CaptureApplication|CoreAudioTap` — zero matches in either.
- `ls MacOSX.sdk/.../Frameworks | grep -iE "audio|capture|record"` lists: `AudioAccessoryKit`, `AudioToolbox`, `AudioUnit`, `AudioVideoBridging`, `AVFAudio`, `CoreAudio`, `CoreAudioKit`, `CoreAudioTypes`, `DiscRecording(UI)`, `ImageCaptureCore`, `ScreenCaptureKit` — no new framework name suggesting a system-audio API shipped alongside macOS 26/27.
- The only WWDC 2025 session that sounded plausible, "Enhance your app's audio recording capabilities" (WWDC25 session 251), turned out to be about **the app's own microphone recording** (input-device picker, AirPods high-quality recording, spatial-audio isolation of the app's own mic input) — not system/process audio capture. Confirmed by fetching the session description directly.
- ScreenCaptureKit's `ScreenCaptureKit.swiftmodule` `.swiftinterface` (64 lines total, `-target arm64e-apple-macos27.0`) contains only the content-sharing-picker configuration struct; the audio-relevant types (`SCContentFilter`, `SCStreamConfiguration`, `SCRunningApplication`) are Objective-C, declared in `SCStream.h` / `SCShareableContent.h`.

Conclusion: as of macOS 27.0, the field really is just Core Audio process taps and ScreenCaptureKit. No higher-level or newer API exists.

## Comparison

| | Core Audio process taps | ScreenCaptureKit |
|---|---|---|
| Isolates one process? | Yes, by construction — HAL exposes per-client `Process` objects (PID + bundle ID) and a tap mixes down an explicit list of them | Yes for video (window ownership); audio scoping to the filtered app(s) is the established behavior but not spelled out in Apple's property-level docs (see "could not verify") |
| Helper-process handling | Manual: enumerate `kAudioHardwarePropertyProcessObjectList`, match by `kAudioProcessPropertyBundleID`, tap all matching PIDs — **or**, macOS 26+, pass `CATapDescription.bundleIDs` + `processRestoreEnabled` and let the HAL track them | Automatic and implicit: caller passes one `SCRunningApplication`; ScreenCaptureKit's own window/app graph (already used for window-ownership across helper processes) is presumably what resolves audio too |
| Buffer format | `AudioStreamBasicDescription` read from `kAudioTapPropertyFormat`, delivered via `AudioDeviceIOProc`/block on the aggregate device — PCM, HAL-native, sample rate follows the source | `CMSampleBuffer` wrapping an `AudioBufferList`, delivered on a dispatch queue via `SCStreamOutput`; rate/channels set by `SCStreamConfiguration.sampleRate` (default 48000) / `channelCount` (default 2) |
| Virtual driver required | No (explicitly the point of the API — see citations) | No |
| Public/supported | Public, documented, has an official sample — but the sample has a filed, unresolved doc bug (`FB17411663`, filed against the same sample) and is sparse | Public, documented, mature since macOS 12.3 (video) / 13.0 (audio) |
| Min macOS | `AudioHardwareCreateProcessTap`/`AudioHardwareDestroyProcessTap`: `API_AVAILABLE(macos(14.2))` per the SDK header (community sources commonly say "14.4" — see note below) | `capturesAudio`/`sampleRate`/`channelCount`/`excludesCurrentProcessAudio`: `macos(13.0)`; `captureMicrophone`: `macos(15.0)` |
| Deprecated by 27? | No deprecation annotation found on any tap symbol | No deprecation on audio-relevant symbols; `SCStreamType`/`streamType` are deprecated (14.0→14.2/15.0) but that's the *video* style enum, not audio |
| TCC permission | "System Audio Recording" (own category) | "Screen Recording" / "Screen & System Audio Recording" — documented to require an app restart after first grant |
| CPU shape | Pure PCM callback, no video/GPU pipeline | Built around a video-capture pipeline; Apple's own sample and 2+ years of forum reports (Oct 2022 → Nov 2024) show audio-only use still needs a `.screen` output configured to avoid dropped/errored streams |

## Core Audio process taps — detail

**Symbols** (all read directly from `CoreAudio.framework/Headers/`):

- `AudioHardwareCreateProcessTap(CATapDescription*, AudioObjectID*)` / `AudioHardwareDestroyProcessTap(AudioObjectID)` — `AudioHardwareTapping.h`, both `API_AVAILABLE(macos(14.2)) API_UNAVAILABLE(ios, watchos, tvos)`.
- `CATapDescription` — `CATapDescription.h`, class itself `API_AVAILABLE(macos(12.0), ios(15.0))`. Init methods: `initStereoMixdownOfProcesses:`, `initStereoGlobalTapButExcludeProcesses:`, `initMonoMixdownOfProcesses:`, `initMonoGlobalTapButExcludeProcesses:`, `initWithProcesses:andDeviceUID:withStream:`, `initExcludingProcesses:andDeviceUID:withStream:` — every one of these takes an `NSArray<NSNumber*>*` of **process `AudioObjectID`s**, i.e. a tap is not limited to one PID; it mixes down a caller-supplied set.
- `CATapDescription.bundleIDs` (`NSArray<NSString*>*`) — **`API_AVAILABLE(macos(26.0))`**. "An Array of Strings where each String holds the bundle ID of a process to tap or exclude."
- `CATapDescription.processRestoreEnabled` (`BOOL`) — **`API_AVAILABLE(macos(26.0))`**. "True if this tap should save tapped processes by bundle ID when they exit, and restore them to the tap when they start up again."
- Process identity: `kAudioHardwarePropertyProcessObjectList` ("An array of AudioObjectIDs that represent the Process objects for all client processes currently connected to the system"), `kAudioHardwarePropertyTranslatePIDToProcessObject`, and per-process properties `kAudioProcessPropertyPID` (`pid_t`), `kAudioProcessPropertyBundleID` (`CFString`), `kAudioProcessPropertyDevices`, `kAudioProcessPropertyIsRunning[Input/Output]` — all in `AudioHardware.h` under "Process Constants"/"Process Properties".
- Aggregate device + tap wiring: `AudioHardwareCreateAggregateDevice`/`AudioHardwareDestroyAggregateDevice` (`AudioHardware.h`, available since 10.9 — predates taps, reused by them), keys `kAudioAggregateDeviceTapListKey` = `"taps"`, `kAudioSubTapUIDKey` = `"uid"`, `kAudioSubTapDriftCompensationKey` = `"drift"`. Reading: `kAudioTapPropertyUID`, `kAudioTapPropertyDescription`, `kAudioTapPropertyFormat` (an `AudioStreamBasicDescription`, "the format of that data that will be accessible in any aggregate device that contains the tap").
- IO delivery: standard HAL device IO — `AudioDeviceCreateIOProcID`/`AudioDeviceCreateIOProcIDWithBlock` + `AudioDeviceStart`/`AudioDeviceStop` on the aggregate device (`AudioHardware.h`, IOProc APIs available since 10.5).

**1. Per-process isolation, and the helper-process problem.** Confirmed true isolation: `kAudioHardwarePropertyProcessObjectList` enumerates individual HAL clients by PID, each independently queryable for its bundle ID. A `CATapDescription` mixes down an explicit array of these — so a caller *can* put "Chrome main + all Chrome helper PIDs" into one tap. The catch, independently confirmed by Chromium's own public design docs, is that **Chrome has run audio output through a separate "Audio Service" process since Chrome v76** (2019) — the tab renderer does not itself own the HAL client, so the caller must find the right PID, not assume it's the main app process. A meeting-recording engineering writeup states the general shape of this problem plainly: "A browser-based meeting runs across multiple processes: main browser process, tab renderer processes, helper processes and GPU processes. The process responsible for meeting audio varies depending on the browser and meeting platform, making it difficult to identify and target the right process or group of processes" ([Recall.ai, "CoreAudioTaps: A deep-dive into the latest version"](https://www.recall.ai/blog/core-audio-taps)). macOS 26's `bundleIDs` + `processRestoreEnabled` additions (above) look purpose-built to solve exactly this — tap by bundle ID and have the HAL keep attaching/reattaching matching processes — but **I found no documentation or real-world usage report describing their exact runtime semantics** (e.g., whether a brand-new helper PID spawned for a newly-opened tab is picked up automatically, or only a process that previously existed and restarted). Treat this as the single largest open question feeding into implementation (see "could not verify").

**2. Buffer format.** `AudioStreamBasicDescription` via `kAudioTapPropertyFormat`, PCM, delivered through a normal HAL `AudioDeviceIOProc`/block callback on the aggregate device — this is the same mechanism as reading from a microphone device, just backed by a tap instead of hardware. Sample rate and channel layout follow the tapped source/device, not a value you set (contrast with ScreenCaptureKit's `sampleRate`/`channelCount`, which you configure).

**3. Virtual driver.** None. Apple's own sample doc frames the tap explicitly as the aggregate-device replacement for that pattern: "This sample code project shows you how to use a tap as an input in a HAL aggregate device, just like a microphone" (Apple Developer Documentation, "Capturing system audio with Core Audio taps", via `DocumentationSearch`). A third-party summary states it more bluntly: "Virtual loopback drivers like BlackHole or Loopback were the default before Core Audio process taps were introduced in macOS 14.2" ([Recall.ai](https://www.recall.ai/blog/core-audio-taps)).

**4. Behavior on device/rate change, or process quit.** This is the weakest-evidenced area, and where the real risk is. An open Apple Developer Forums thread (825780, "AudioHardwareCreateProcessTap deli[vers]...") reports process taps **silently degrading to all-zero PCM buffers** after several minutes of otherwise-normal callbacks, while other apps keep producing audible output on the same device — the callback keeps firing with valid timestamps/byte counts, but every sample is `0.0f`. Community discussion around that thread correlates the failure with **output sample-rate renegotiation** (e.g. 44.1kHz ↔ 48kHz, which can be triggered by another app changing the active output device), and the only reported reliable fix is to **destroy and recreate both the process tap and the aggregate device** — restarting just the IOProc or just the aggregate device isn't enough. Separately, an unrelated real-world bug report shows a Core Audio tap producing **silent, zero-filled buffers specifically against Microsoft Teams**, while ScreenCaptureKit-based competitors captured the same app's audio successfully ([pasrom/meeting-transcriber#79](https://github.com/pasrom/meeting-transcriber/issues/79)) — root cause unresolved, but it's a concrete existence proof that taps aren't universally reliable against every multi-process/real-time-audio app. Teams is architecturally a WebRTC conferencing app, not a simple HTML5-media-playback case like the two named targets (Chrome/YouTube, Safari/Bilibili), so this is a caution flag rather than a disqualifier — but it means "does the tap survive Chrome switching tabs / changing output device / Safari's video ending" needs to be validated empirically, not assumed from the header docs.

**5. CPU cost.** No quantitative benchmark found from any source (Apple or third-party). Qualitatively, it's the lighter of the two architecturally — a raw PCM callback with no video frame, IOSurface, or window-compositing machinery involved, versus ScreenCaptureKit's capture pipeline (see below). This is reasoned from architecture, not measured — flagged in "could not verify."

**6. Public/supported vs private.** Fully public, no private symbols. But real-world documentation quality is poor: Apple's *own* official sample code has an open, unaddressed bug report — a developer showed that the sample calls `AudioObjectSetPropertyData`/`AudioObjectGetPropertyData` for `kAudioAggregateDevicePropertyTapList` against the **tap's** `AudioObjectID` when the property actually belongs to the **aggregate device's** `AudioObjectID`; filed as Feedback `FB17411663` in September 2025, no Apple reply as of that thread ([forum thread 798941](https://developer.apple.com/forums/thread/798941)). There is also no official API to query current permission status ahead of time — "there is no way to query or request the state of this permission... using official APIs. If the permission is not granted, you will receive silence" ([forum thread 771864](https://developer.apple.com/forums/thread/771864); Apple DTS confirms permission is requested implicitly on first aggregate-device start, with no proactive check).

**7. Min macOS / deprecation.** `AudioHardwareCreateProcessTap`/`AudioHardwareDestroyProcessTap` are annotated `API_AVAILABLE(macos(14.2))` in the macOS 27.0 SDK header — note this **contradicts the widely-repeated community figure of "macOS 14.4"** (seen in `insidegui/AudioCap`'s README, the TypeWhisper migration issue, and others). I could not resolve why the popular figure differs from the header; a plausible explanation is that the symbol existed in the 14.2 SDK/beta but was non-functional until the 14.4 release, but I found no source confirming this — flagged as unverified. Not version-relevant to this app (target is 27.0-only), but worth carrying into the ADR as a documented discrepancy. No deprecation annotations found on any process-tap symbol as of the 27.0 SDK.

## ScreenCaptureKit — detail

**Symbols** (read directly from `ScreenCaptureKit.framework/Versions/A/Headers/SCStream.h` and `SCShareableContent.h`):

- `SCContentFilter` — class `API_AVAILABLE(macos(12.3), ..., ios(27.0), ...)`. Every initializer capable of including/excluding an app (`initWithDisplay:includingApplications:exceptingWindows:`, `initWithDisplay:excludingApplications:exceptingWindows:`) requires an `SCDisplay` — **there is no initializer that captures audio from an app without anchoring to a display**, i.e. the filter is fundamentally display/window-shaped even when your goal is audio-only.
- `SCStreamConfiguration.capturesAudio` (`BOOL`, `macos(13.0)`), `.sampleRate` (`NSInteger`, default 48000, `macos(13.0)`), `.channelCount` (`NSInteger`, default 2, `macos(13.0)`), `.excludesCurrentProcessAudio` (`BOOL`, `macos(13.0)`), `.captureMicrophone` (`BOOL`, `macos(15.0)`), `.microphoneCaptureDeviceID` (`macos(15.0)`).
- `SCRunningApplication` — `bundleIdentifier` (`NSString*`), `applicationName` (`NSString*`), `processID` (single `pid_t`) — note this is **one PID per app object**, not an array; there is no header-level statement of how (or whether) helper-process audio is attributed back to this object.
- `SCStreamOutputType` enum: `.screen`, `.audio` (`macos(13.0)`), `.microphone` (`macos(15.0)`) — delivered via `SCStreamOutput.stream(_:didOutputSampleBuffer:of:)`, a `CMSampleBuffer` wrapping an `AudioBufferList` per the type comment in `SCStream.h`.

**1. Per-process isolation.** `SCContentFilter(display:including:[SCRunningApplication], exceptingWindows:)` scopes *video* to windows owned by the listed apps — that part is explicit and documented. Whether the accompanying **audio** output is limited to just those apps, versus the whole system mix, is the established community understanding (multiple independent secondary sources describe it this way) but I could not find an Apple property-level doc sentence that says so explicitly for the include/exclude-application initializers — flagged under "could not verify." `excludesCurrentProcessAudio` (a boolean, not a list) at least proves *some* per-process audio filtering is real in the implementation. On the helper-process question specifically: `SCRunningApplication` exposes only one `pid_t`, but ScreenCaptureKit's app/window enumeration already has to solve "which windows belong to Chrome despite living in a helper process" for its *video* capture to work at all (window ownership across helper processes is a solved problem for screen recorders generally) — so it's plausible SCK's audio path piggybacks on the same app-attribution logic rather than requiring the caller to enumerate PIDs. This is inference, not a documented guarantee.

**2. Buffer format.** `CMSampleBuffer` → `AudioBufferList` → (per Apple's own sample) converted to `AVAudioPCMBuffer` using an `AVAudioFormat` built from `sampleRate`/`channelCount` you set on `SCStreamConfiguration` (defaults 48000 Hz / 2 channels) — delivered asynchronously on whatever `dispatch_queue_t` you pass to `addStreamOutput(_:type:sampleHandlerQueue:)`.

**3. Virtual driver.** None required — same conclusion as Core Audio taps.

**4. Audio-only is a second-class mode, with a real CPU/architecture cost.** Apple's own official sample code (`Capturing screen content in macOS`, associated with WWDC24 session 10088) always calls `addStreamOutput(_:type:.screen,...)` alongside `.audio`, even when audio is what's wanted. A long-running Apple Developer Forums thread (718279; original post Oct 2022, still being answered as late as Nov 2024) documents developers hitting `stream output NOT found. Dropping frame` errors and stream failures when they try to configure `SCStream` for audio only without a video output, with the practical workaround being to keep a `.screen` output attached and either filter the frames out in the callback or set `minimumFrameInterval` very large (e.g. 0.1 fps) to suppress most of the cost — not eliminate it. The accepted answer in that thread is literally "use `AudioHardwareCreateProcessTap` instead." This means, for a menu-bar app whose whole job is audio-only, ScreenCaptureKit likely carries hidden video-pipeline cost (frame compositing / IOSurface machinery) that Core Audio taps simply don't have.

**5. CPU cost.** No audio-only-specific number found. General ScreenCaptureKit marketing/community claims describe it as GPU-accelerated and low-CPU for its intended (video) use case, which doesn't answer the audio-only question above.

**6. Public/supported vs private.** Fully public, documented, mature (`capturesAudio` et al. since macOS 13.0). More mature/stable documentation than Core Audio taps.

**7. Min macOS / deprecation.** Audio-relevant symbols: 13.0 (`capturesAudio`, `sampleRate`, `channelCount`, `excludesCurrentProcessAudio`), 15.0 (`captureMicrophone`, `microphoneCaptureDeviceID`). `SCStreamType`/`.streamType` are deprecated in favor of `SCShareableContentStyle`/`.style` (14.0 → 14.2/15.0) but that's the video-style enum, not an audio symbol — no audio-relevant deprecations found as of the 27.0 SDK. Apple's sample project itself requires "macOS 15 or later" and documents a **mandatory app restart after the first Screen Recording permission grant** — a real, first-party-documented UX cost this app would inherit.

## Rejected: ScreenCaptureKit

Rejected for this app specifically (audio-only, menu-bar, local, one chosen app) — not because it's broken, but because it's the wrong shape:

- It is architected around screen sharing; audio-only use is a workaround (attach `.screen`, filter/throttle it away) rather than a first-class mode, per Apple's own sample and a 2+-year-old, still-live forum thread.
- It requires the heavier "Screen Recording" TCC permission, which Apple's own docs say forces an app restart after the first grant — a bad first run for a one-click menu-bar recorder.
- Its per-app audio scoping across a browser's helper processes is plausible but not documented at the property level — it would need the same empirical validation Core Audio taps needs, without the compensating benefit of a lighter permission or an audio-only architecture.

It remains a credible fallback if the prototype spike finds Core Audio taps unreliable against Chrome/Safari specifically (unlike the Teams case, our two named targets are simple HTML5 media playback, which is a better-trodden path for taps — see `AudioCap`, `AudioTee`, `hyprnote`, all of which use taps successfully for meeting/browser audio).

## What I could not verify

- **Exact runtime semantics of `CATapDescription.bundleIDs` / `processRestoreEnabled` (macOS 26+).** The SDK header documents *what* they do in one sentence each, but I found zero real-world usage reports, sample code, or Apple documentation elaborating on *when* a newly-spawned helper process (e.g., a fresh Chrome renderer/audio-service PID for a just-opened tab) gets picked up by a bundle-ID-based tap, versus only processes that previously existed and restarted. This is the single most important gap for this app's architecture and should be closed with a small prototype before the recording feature is built.
- **Whether ScreenCaptureKit's audio actually scopes to the app(s) passed to `includingApplications`/`excludingApplications`, or captures the whole system mix regardless.** Widely believed true in community writing, not found stated explicitly in Apple's own property-level docs for that exact combination.
- **Exactly which OS process actually owns the CoreAudio HAL client for Chrome's or Safari's tab audio** — confirmed that Chrome's audio output runs in a separate "Audio Service" process (Chromium's own public design docs, since v76) and that this varies "depending on the browser and meeting platform" per a third-party engineering writeup, but I did not find a citable, current list of the actual bundle identifiers/process names involved (e.g., whether Chrome's audio-service helper shares Chrome's main bundle ID or uses a distinct one) for either Chrome or Safari on macOS 27 specifically. Needs direct empirical inspection (e.g., dumping `kAudioHardwarePropertyProcessObjectList` while YouTube/Bilibili play) rather than documentation.
- **Quantitative CPU cost for either API**, audio-only. No benchmark numbers found from Apple or third parties for either candidate; the comparison above is architectural reasoning, not measurement.
- **Behavior when the tapped output device changes mid-recording**, beyond the sample-rate-renegotiation bug already cited. Not documented by Apple either way for taps or for ScreenCaptureKit.
- **Why community sources consistently cite "macOS 14.4" for `AudioHardwareCreateProcessTap`** when the installed 27.0 SDK header says `macos(14.2)`. Noted as an open discrepancy, not resolved.
- Did not build or run code against this SDK to confirm any of the above experimentally — this is a documentation/header-research ticket, not a prototype. A prototype spike is the natural next step and is explicitly recommended above.
