# Export runs non-blocking in the inspector, and navigating away from the Recording cancels it

Export is **not modal**. It runs in the trailing Export inspector [ADR-0006](0006-the-library-is-a-folder.md)'s save panel feeds, with the Export button itself becoming the running control, and the editor stays fully live around it. It writes to a **sibling temporary file in the destination directory** and finishes with an atomic `replaceItemAtURL:`, so the file the user chose is never touched until the encode has succeeded. It is **cancellable**, and it cancels **on its own** whenever the user navigates away from the Recording being exported — closing the editor, selecting another Recording, or quitting. Only **one** Export runs at a time.

The forcing fact is speed. On this machine `afconvert` encodes Float32 stereo at 48 kHz at **205–290× realtime** across all four Quality Presets — a 10-minute Recording exports in 2–3 s, an hour in under 20 s, and the 3-hour amber-Runway Recording [ADR-0009](0009-the-disk-guard-is-a-runway-clock.md) warns about in roughly a minute. [Issue #9](https://github.com/SamWongML/macos-audio-recording/issues/9) sized this as "seconds to minutes"; it is the seconds end. A modal sheet that seizes the window for two seconds costs more than it tells.

## Considered options

**Blocking modal sheet with a progress bar** was rejected on those timings. At 2–3 s the sheet is a flash of chrome, and it forfeits the one thing [issue #7](https://github.com/SamWongML/macos-audio-recording/issues/7) built for: a permanently visible Export inspector, already on screen, already the home of the live size estimate. The running state lands there for free.

**Encoding straight to the URL the save panel returns** was rejected because it has a real data-loss path. `NSSavePanel.URL` is read-only: the panel hands back a location and writes nothing itself, so a failure or a cancel mid-write leaves a truncated file exactly where the user's existing file used to be. Encoding to a **sibling** temp in the same directory — not the system temp dir, which may be on another volume and defeat the atomic swap — and finishing with `replaceItemAtURL:` keeps the destination pristine until the last instant. `NSSavePanel` presenting its own overwrite confirmation does not change this: it confirms intent, it does not perform or defer the write.

**A queue, or concurrent Exports,** were rejected together. The running state *is* the button, so a second Export has nowhere to present itself; two encodes competing for the same cores make both progress readings dishonest; and a queue is a v2 answer to a v1 operation that finishes in seconds. One at a time, app-wide.

**A confirmation before cancelling** — on window close or Recording switch — was rejected as the wrong tax. Because the destination file is untouched until the swap, a cancelled Export costs only up to ~20 s of perfectly reproducible work. That is strictly less than what this app already discards unwarned: [ADR-0007](0007-mid-recording-faults-are-seams-not-stops.md) has quit stop and save a Recording, and [ADR-0004](0004-nsstatusitem-not-menubarextra.md) accepts an unconfirmed left-click ending one — both destroying something irreplaceable. Guarding a redoable encode while those stand would be incoherent.

**Freezing the editor's Trim, preset and Gain during an Export** was rejected for the same reason the sheet was: it disables a live surface for a two-second job. Instead the Export **snapshots its parameters at launch** and later edits never reach the running encode. The one accepted wrinkle is that [issue #9](https://github.com/SamWongML/macos-audio-recording/issues/9)'s size estimate keeps recomputing as a handle is dragged, so mid-Export the readout can describe a file other than the one being written — tolerable because the running control sits directly above it showing real progress of the real file.

## Consequences

**The Export button is a determinate progress control, in place, immediately on click.** Exact frame counts are available because the encode is a hand-rolled `ExtAudioFileWrite` loop over the master's frames, not an opaque `AVAssetExportSession`, so progress is real rather than estimated and there is no reason to delay showing it. A delayed or indeterminate indicator would leave the first half-second unacknowledged and invite a second click. When [issue #24](https://github.com/SamWongML/macos-audio-recording/issues/24)'s normalization is on, Export is strictly **measure-then-encode** — integrated loudness over the trimmed range must be known in full before the correction constant exists — so the two serial passes show as **one continuous bar**, weighted by their measured ratio and labelled by phase. This roughly doubles wall-clock and still finishes under a minute at the worst legitimate length.

**Success is told in the window; failure is told louder.** A completed Export returns the inspector to idle with a transient confirmation and a Reveal in Finder affordance — a two-second user-initiated job does not warrant a notification, and the file is simply there. A **failure** is told in-window and, when the app is not frontmost, **also as a notification**, because a silent failure at second 40 while the user is in another app is the one outcome that must not be missable. Where notification authorization was denied, the in-window telling still carries it, as [ADR-0010](0010-silence-never-ends-a-recording.md) already falls back for the degraded-Recording case.

**Export pre-flights disk space and refuses rather than fills it.** Before writing it compares [issue #9](https://github.com/SamWongML/macos-audio-recording/issues/9)'s estimate against `statfs` free space on the **destination** volume, which can be any volume, not the Library's that [ADR-0009](0009-the-disk-guard-is-a-runway-clock.md)'s Runway clock watches. Deliberately a **byte comparison, not a Runway clock**: Export is bounded work of known size, so the argument that sent capture to a time unit does not apply here. This turns the ugliest failure — the disk filling mid-encode, leaving a partial temp and an unclear message — into a refusal that names the problem before any bytes are written. A genuine `ENOSPC` slipping past the estimate's ±3.5% still surfaces as a plain failure per the telling above, and the sibling temp is discarded, so the destination is never left partial.

**An Export may run during a capture, and the capturing Recording is not itself exportable.** The encode always runs at `.utility` QoS, which by construction cannot preempt the capture IOProc: Core Audio IO threads run in a realtime `os_workgroup` interval (`kAudioDevicePropertyIOThreadOSWorkgroup`), a time-constraint scheduling class above every QoS band. If disk contention — reading a master back while writing a new one at 1.4 GB/hour — ever starved the writer, that is not a new hazard but [ADR-0010](0010-silence-never-ends-a-recording.md)'s callback-famine hard fault, which already ends the Recording with a Seam and a notification. The QoS separation is asserted from the platform's documented scheduling structure rather than measured under live contention. Separately, the Recording currently being captured cannot be exported at all: its `.caf` is still growing in place per [ADR-0006](0006-the-library-is-a-folder.md) and its Trim end is undefined until Stop.

Settled in issue #27.
